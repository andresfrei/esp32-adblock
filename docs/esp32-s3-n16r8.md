# ESP32-S3 N16R8 operations

This is a **provisional, software-only** runbook for the queried ESP32-S3 v0.2,
16 MiB flash and reported 8 MiB PSRAM. The physical PCB, USB topology, and
hardware acceptance are still unconfirmed.

## Initial blocklist evidence

The reproducible first-list command is:

```bash
python3 tools/build_blocklist.py data/blocklist.bin \
  --max-domains 140000 \
  --require-domain doubleclick.net \
  --report docs/blocklist-build.json
```

The generator defaults to these required sources when no source arguments are
provided:

- StevenBlack base: `https://raw.githubusercontent.com/StevenBlack/hosts/master/hosts`
- HaGeZi Light domains: `https://raw.githubusercontent.com/hagezi/dns-blocklists/main/wildcard/light-onlydomains.txt`

The current local generation in [`blocklist-build.json`](blocklist-build.json) is:

| Measure | Result |
| --- | ---: |
| normalized source union | 92,982 domains |
| selected first list | 92,982 domains |
| cap | 140,000 maximum |
| truncated | no |
| unique 40-bit records | 92,982 |
| collisions | 0 |
| blob size | 464,910 bytes |
| blob SHA-256 | `659c880f1a6c0b52e84b627205fafb7168e84a996cba496a6a42f57d57b9a905` |

Counts are time-varying feed-download evidence, not a promise of the 140,000
cap and not a full-feed recount. The report separates official HaGeZi metadata
from this run's downloaded bytes, timestamps, digests, and parser counts. The
official reference is the HaGeZi README and its WildcardDomains URL; its header
metadata says 39,661 entries, while this run accepted 39,661 records from that
source. No source dump is tracked. `doubleclick.net` is present in the
local hash blob (`0xcd127775cd`); `github.com` is absent
(`0xdbc7755d59`). These are offline membership checks, not DNS or hardware
results.

Per-source validation is fail-closed: every required source must produce at
least one valid domain, HTTP 200 HTML/error payloads are rejected, and a failed
or empty source leaves both previous output files untouched. Report counters are
explicit: `raw_line_count` counts every decoded line; `candidate_record_count`
counts supported hosts/plain/simple-ABP candidates; `accepted_record_count`
counts candidates after production-compatible validation; `normalized_domain_count`
is unique accepted domains; rejected and skipped counters cover invalid
candidates and unsupported/comment lines respectively. Full ABP exceptions,
regexes, and URL/path rules are skipped rather than claimed compatible.

The output remains exactly five-byte little-endian FNV-1a40 records, numerically
sorted and unique, matching the firmware constants. The cap is only a maximum:
selection includes required domains first, then lexicographically fills the cap,
and never pads the result. An uncapped generation is available for a deliberate
future decision, but this task does not switch to a larger feed or fabricate
140,000 entries.

## Build-only checks

Use the isolated PIO from this checkout when available:

```bash
PIO="$HOME/.local/share/esp32-adblock-tools/platformio-venv/bin/pio"
"$PIO" run -e c3
"$PIO" run -e s3_n16r8
"$PIO" run -e s3_n16r8 -t buildfs
```

Generic PlatformIO installations use the same commands with `pio` instead of
`"$PIO"`. The build environments are `c3` and `s3_n16r8`; bare `pio run`
continues to select C3. The S3 artifacts are:

- `.pio/build/s3_n16r8/firmware.bin`
- `.pio/build/s3_n16r8/littlefs.bin`
- `data/blocklist.bin` (the source data included by `buildfs`)

Serial is the observed UART0 route at **115200 baud**, with
`ARDUINO_USB_MODE=0` and `ARDUINO_USB_CDC_ON_BOOT=0`. A monitor example is:

```bash
PORT=/dev/serial/by-id/usb-1a86_USB_Single_Serial_5C37178676-if00
"$PIO" device monitor -p "$PORT" -b 115200
```

The by-id path is an example of the required form, not a confirmed universal
port. Do not substitute a guessed `/dev/tty*` path.

## First device upload (not performed)

Uploading requires a separate explicit decision after the board, wiring, and
recovery path are confirmed. Use the confirmed by-id port only:

```bash
"$PIO" run -e s3_n16r8 -t upload --upload-port /dev/serial/by-id/<confirmed-board>
```

If the confirmed board does not enter download mode automatically, the manual
fallback is: hold **BOOT**, tap **RESET**, release **BOOT** when the uploader
starts connecting, and use the same confirmed port. No reset, erase, upload, or
hardware command was run for this software task.

`buildfs` only creates the local filesystem image. Runtime mounting calls
`LittleFS.begin(false)`: a fresh firmware with no valid filesystem therefore
needs an explicitly authorized initial `uploadfs`, while a device with a valid
existing filesystem does not need one. The device operation is destructive:

```bash
"$PIO" run -e s3_n16r8 -t uploadfs --upload-port /dev/serial/by-id/<confirmed-board>
```

It replaces the filesystem and wipes persisted filesystem contents, including
lists and settings. It is not a normal list update and must not be used as an
OTA shortcut.

## Normal updates and rollback boundaries

- **Firmware-only OTA:** in the dashboard's OTA panel, load
  `.pio/build/s3_n16r8/firmware.bin`. Do not repartition and do not upload the
  filesystem for a firmware-only update. The installed partition table must
  remain the S3 table; this preserves LittleFS data and NVS configuration,
  including saved Wi-Fi credentials and upstream settings.

### S3 network profile trial and confirmation

The S3-only network panel and setup portal use the N1 `network/profile` record
(one 68-byte NVS value). DHCP is the default and remains available as an
explicit choice; `192.168.5.5/24`, gateway `192.168.5.1`, and resolver
`1.1.1.1` are UI examples, not firmware defaults.

Exact change flow:

1. Open the S3 dashboard at its current IP and select DHCP or enter all static
   fields. Submit the network form with its explicit intent marker.
2. The server validates the complete profile before writing NVS, stores a
   pending candidate, sends the HTTP response, and only then schedules the
   restart. It never applies a network change synchronously inside the POST.
3. Reconnect at the server-reported **new URL**. The dashboard status is
   authoritative and shows the current IP, trial state, revision/token, and
   remaining time. Press **Confirm** explicitly from that new address within
   180 seconds; there is no automatic success.
4. If confirmation does not commit, the helper persists the previous profile
   before scheduling a restart. An unconfirmed reboot also rolls back through
   the helper rather than starting a fresh deadline. A storage I/O or
   readback-indeterminate result does not reboot; it remains visible as a
   recovery/storage error.

Confirmation is bound to the server socket's local IP, revision, and expected
candidate IP. Host headers, old tabs, stale revisions, non-POST requests, and
cross-origin requests cannot confirm another trial. The network endpoints are
intentionally unauthenticated on the LAN, like the existing API boundary; they
add same-origin checks where Origin/Referer/Host are available and require an
explicit intent marker, not a general authentication system. No credentials are
returned in status, query strings, or logs.

If the new Wi-Fi credentials are wrong, the device returns to the setup portal;
that is a credential-connection outcome, not a network-profile rollback and it
does not copy the previous SSID or password. The portal services the same
180-second deadline even while station connection has failed. Static candidates
are rejected when their local IP equals the configured upstream DNS address,
and the profile helper rejects a resolver equal to the local IP. Router
reachability, duplicate-IP detection, and gateway correctness beyond syntax
and subnet validation are not claimed.

Do not use the physical BOOT button or hardware reset as a confirmation step.
This software-only task does not flash, reset, or validate hardware; N3
connection/factory-reset handlers are a separate unit.

### Captive portal Wi-Fi selection

The setup portal now renders the current scan as a visible selector instead of
an HTML datalist. It scans the existing maximum of 15 2.4 GHz networks, keeps
SSID bytes/case/spaces unchanged, and escapes unsafe SSID characters for HTML.
When the scan is empty, the page says so and still offers a manual hidden-network
entry. The manual field uses a separate mode, so it cannot collide with a real
scanned SSID; `POST /wifisave` remains compatible with the existing `s` and `p`
fields. Scanned selections are checked against the current scan, while manual
SSID input is accepted exactly as entered; blank or unscanned selections return
HTTP 400 before NVS is changed. This is a portal/UI and validation change only;
it does not claim to fix an underlying LAN, DHCP, mDNS, or station-connection
problem. No rescan or asynchronous networking was added.

The later firmware-only update should install only the S3 firmware image and
must not upload a filesystem image or reset the device. Preserve the T2/T3
partition, filesystem, credential, list, and upstream-configuration boundaries.
- **CLI OTA:** the PlatformIO `espota` form is documented, but has not been
  hardware-verified here. Use it only after the target firmware's OTA endpoint
  and transport are confirmed:
  `"$PIO" run -e s3_n16r8 -t upload --upload-port <device-ip> --upload-protocol espota`.
- **Blocklist panel/URL update:** load `data/blocklist.bin` (the panel writes a
  validated `blocklist.new` candidate), or configure the remote URL. The
  candidate must have a known `Content-Length`; chunked or unknown-length
  responses are rejected. The current list stays active until candidate
  validation and rename succeed.
- **`uploadfs`:** destructive replacement of the entire filesystem; it is the
  boundary that can remove the current list and persisted filesystem settings.
- **NVS upstream setting:** a readback verification failure returns HTTP 500 and
  keeps the old upstream active in RAM, but the new candidate may remain in NVS;
  there is no guaranteed NVS rollback. Firmware-only OTA and list updates do
  not erase NVS. A full flash erase would.

The C3 filesystem is only 1,376,256 bytes. Two approximately 700 kB lists
(roughly a 140k-domain live list plus a 140k-domain candidate) do not fit, so
C3 refuses the update safely without deleting the live list. The S3 layout has
the required headroom, but still needs space for settings and candidate
validation.

The firmware's remote HTTPS fetch currently uses its existing `setInsecure()`
limitation: ordering and length checks are structural integrity checks, not
source authenticity or signatures. The Python generator uses standard-library
HTTPS certificate verification and has no insecure bypass. Neither path proves
that a feed is trustworthy.

## Network and router operation

1. Join the setup AP `C3-AdBlock-XXXX` if station Wi-Fi is not configured; use
   its captive portal. After station setup, use `http://c3adblock.local` or
   `http://<ESP-IP>` for the dashboard and panel.
2. Reserve the current **station MAC** in the router's DHCP server. Read the
   station MAC from the device diagnostic; do not assume the USB/UART bridge
   ID is the Wi-Fi station MAC.
3. In the router's **LAN DHCP/DNS** settings, advertise the reserved ESP IP as
   DNS. Do not leave the ISP DNS as the only advertised resolver and do not add
   a public secondary resolver that bypasses blocking.
4. Do not configure the router itself as the ESP upstream if that router sends
   DNS requests back to the ESP; that creates a forwarding cycle. Choose a
   separate reachable IPv4 upstream in the dashboard.

IPv4 port 53 is the tested design boundary. IPv6 clients, DHCPv6-advertised
DNS, encrypted DNS (DoH/DoT), browser secure-DNS settings, VPNs, and clients
with their own resolver can bypass this IPv4 DHCP-DNS path. They need separate
network policy; this firmware does not claim to intercept them.

## Offline membership smoke test

After generating the blob, check the static hash contract without a device:

```bash
dig @<ESP-IP> doubleclick.net A
dig @<ESP-IP> github.com A
```

Expected interpretation once hardware is available: `doubleclick.net` is in the
static list, so an A query should be sinkholed to `0.0.0.0` (a client/resolver
may instead surface an NXDOMAIN-style blocked result); `github.com` is not in
the static list, so it should be forwarded and return the upstream's normal answer
when the upstream is reachable. A `0.0.0.0`/NXDOMAIN result for the first query
is only a static blocking interpretation until a real DNS exchange is observed;
this work has no hardware DNS result and makes no latency claim.
